# Evidence 09 — Ручные проверки web/API

Ручные негативные сценарии выполнялись только против локального backend `http://127.0.0.1:9999`. Использовались безопасные запросы без массового перебора и без внешних целей.

| ID | Проверка | Фактический результат | Статус |
|---|---|---|---|
| API-NEG-01 | `GET /api/products/999999` | `404 Not Found`, минимальный JSON без stack trace | `PASS` |
| API-NEG-02 | `GET /api/products/abc` | `400 Bad Request`, без внутренних деталей | `PASS` |
| API-AUTHZ-01 | `DELETE /api/products/1` без токена | `200 OK`; повторный GET вернул `404`, удаление подтверждено | `FINDING` |
| API-NEG-03 | malformed JSON на `/api/users/registration` | `400 Bad Request`, без parser/framework exception details | `PASS` |
| API-NEG-04 | `PUT /api/products/1` | `405 Method Not Allowed`, `Allow: GET, DELETE` | `PASS` |
| API-NEG-05 | anonymous `POST /api/media` с `text/plain` | `403 Forbidden`; до проверки типа файла запрос не дошёл | `PASS` для anonymous access |
| API-AUTHZ-02 | anonymous `GET /api/orders/{id}`, IDs 1..20 | все `404`; существующий заказ не найден | `INCONCLUSIVE` |

Полный санитаризированный листинг запросов и ответов: [negative-tests.txt](./negative-tests.txt).

## Основной вывод

Обработка несуществующих объектов, некорректных типов path-параметров, malformed JSON и неподдерживаемого HTTP-метода не раскрывает stack trace или внутренние Java/Spring детали в рассмотренных ответах.

При этом динамически подтверждена серьёзная проблема контроля доступа: `DELETE /api/products/{id}` выполняется без `Authorization` и реально удаляет товар. Этот результат был воспроизведён повторно после сброса Compose-стенда. Находка была ранее выявлена при review исходного кода и должна быть окончательно классифицирована в пункте 10 с матрицей ролей.

Анонимная загрузка `/api/media` корректно блокируется `403`, однако этот тест не подтверждает проверку MIME-типа для авторизованного пользователя, поскольку запрос был отклонён на этапе авторизации.

Проверка `GET /api/orders/{id}` остаётся неубедительной: в текущем стенде отсутствовал существующий заказ, поэтому полученные `404` нельзя считать ни `PASS`, ни подтверждением обхода авторизации.

После перезапуска backend дополнительно подтверждено логирование сгенерированных admin credentials в `WARN`; значение credential не сохраняется в evidence. Это подтверждение ранее зафиксированной проблемы логирования, а не отдельная новая находка пункта 9.

## Статус

`FINDING / IN PROGRESS` — базовые негативные API-сценарии проверены; подтверждено анонимное удаление товара. Для завершения пакета остаются дополнительные ручные проверки валидации/ошибок и сценарии, требующие тестовой авторизации. Role/object access и authentication/session scenarios учитываются в пункте 10.
